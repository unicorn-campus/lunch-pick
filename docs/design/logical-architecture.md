## 1. 개요

### 1.1 설계 원칙

| 원칙 | 설명 |
|------|------|
| **YAGNI** | MVP에 필요한 최소한의 서비스 경계만 정의. 물리 배포 구조와 인프라 상세는 이 단계에서 결정하지 않는다. |
| **유저스토리 정렬** | 모든 서비스 경계와 통신 경로는 UFR(유저 기능 요구사항)에 대응하는 근거가 있어야 한다. |
| **AI 격리** | AI Pipeline을 독립 서비스로 분리하여 LLM 의존성이 다른 서비스로 전파되지 않도록 한다. |
| **폴백 우선** | LLM 장애 시 서비스가 중단되지 않도록 모든 AI 호출 경로에 폴백 전략을 명시한다. |
| **단일 진입점** | 클라이언트는 API Gateway 하나를 통해서만 서비스에 접근한다. |

### 1.2 핵심 컴포넌트 정의

| 컴포넌트 | 역할 | 핵심 솔루션 연결 |
|---------|------|---------------|
| **클라이언트** | React 웹 / 모바일 앱. 사용자 인터페이스 전담. API Gateway 외 직접 서비스 접근 없음. | A5(원탭 기록), A8(추천 근거 표시) |
| **API Gateway** | 단일 진입점. JWT 검증, TLS 종료, 라우팅, Rate Limiting 공통 적용. | - |
| **회원 서비스** | 카카오 소셜 로그인, 취향 프로파일 관리, 위치 동의, 알레르기 필터, 구독 상태 관리. | A1(취향 해자) |
| **추천·이력 서비스** | 오늘의 추천 3개 조회, 추천 수락/거절, 식사 원탭 기록, 피드백, 취향 학습 배치, 이력 타임라인. | A1, A5, A8 |
| **결제 서비스** | 구독 플랜 조회, PG 결제, 구독 해지, 구독 상태 이벤트 발행. | A1(구독 모델) |
| **AI Pipeline 서비스** | LLM API 호출, 프롬프트 관리, 추천 이유 자연어 생성, 확신 스코어 계산, 폴백 추천. | A8 |
| **Redis Cache** | 추천 결과 캐싱(TTL: 당일 13:00), 세션, JWT 블랙리스트. | Cache-Aside 패턴 |
| **PostgreSQL (서비스별)** | 각 서비스 전용 독립 DB. 다른 서비스 DB에 직접 접근 금지. | - |
| **메시지 큐** | Redis Streams 기반 경량 큐. 결제 성공 → 회원 구독 상태 갱신 비동기 처리. | Queue-Based Load Leveling |

## 2. 서비스 아키텍처

### 2.1 서비스별 책임

#### 회원 서비스 (member-service)

| 분류 | 내용 |
|------|------|
| **대응 UFR** | UFR-MBR-010~050 (소셜 로그인, 온보딩 퀴즈, 위치 동의, 알레르기 설정, 프로필 수정) |
| **핵심 책임** | 카카오 OAuth 2.0 인증 위임, 초기 취향 벡터 생성(온보딩 퀴즈 결과), 알레르기 하드 필터 등록, 구독 상태 관리 |
| **데이터 소유** | 회원 정보, 취향 벡터, 알레르기/식이제한, 위치 동의 이력, 구독 상태 |
| **외부 의존** | 카카오 로그인 API (Circuit Breaker + Retry 적용) |
| **적용 패턴** | Federated Identity, Circuit Breaker(카카오), Retry(카카오), Health Endpoint Monitoring |

**책임 경계**: 회원 서비스는 추천 결과를 직접 생성하지 않는다. 취향 벡터를 보관하고, 추천·이력 서비스의 조회 요청에 응답하는 역할만 담당한다.

#### 추천·이력 서비스 (recommendation-service)

| 분류 | 내용 |
|------|------|
| **대응 UFR** | UFR-REC-010~120 (추천 조회, 추천 이유, 콜드스타트, 수락/거절, 길찾기, 식사 기록, 피드백, 취향 학습, 이력 조회, 인사이트) |
| **핵심 책임** | 오늘의 추천 3개 조회 오케스트레이션, AI Pipeline 호출, 캐시 히트/미스 판단, 식사 이력 저장, 피드백 저장, 일일 취향 학습 배치(매일 03:00), 취향 인사이트 집계 |
| **데이터 소유** | 추천 이력, 식사 기록, 피드백, 일별 취향 벡터 스냅샷 |
| **외부 의존** | AI Pipeline 서비스(동기 REST), 지도 API(Circuit Breaker), 날씨 API(Circuit Breaker + Retry) |
| **적용 패턴** | Cache-Aside(추천 캐싱), Circuit Breaker(AI Pipeline, 지도, 날씨), Retry(AI Pipeline, 날씨), Rate Limiting(LLM 글로벌 제한), Health Endpoint Monitoring |

**책임 경계**: 추천·이력 서비스는 LLM을 직접 호출하지 않는다. AI Pipeline 서비스에 추천 컨텍스트를 전달하고 결과를 수신하는 오케스트레이터 역할을 한다.

#### 결제 서비스 (payment-service)

| 분류 | 내용 |
|------|------|
| **대응 UFR** | UFR-PAY-010~030 (구독 플랜 조회, 구독 결제, 구독 해지) |
| **핵심 책임** | 구독 플랜 정의 및 조회, PG 연동 결제 처리, 청약철회권 7일 보장, 구독 상태 변경 이벤트 발행 |
| **데이터 소유** | 구독 플랜, 결제 이력, 청약철회 기록 |
| **외부 의존** | PG(결제 게이트웨이) — Circuit Breaker 적용, Retry 미적용(이중결제 방지) |
| **적용 패턴** | Circuit Breaker(PG), Health Endpoint Monitoring, Queue-Based Load Leveling(경량: Redis Streams로 구독 상태 갱신 이벤트 발행) |

**책임 경계**: 결제 서비스는 회원의 구독 상태를 직접 변경하지 않는다. 결제 성공 이벤트를 메시지 큐에 발행하면, 회원 서비스가 이를 소비하여 구독 상태를 갱신한다.

#### AI Pipeline 서비스 (ai-pipeline-service)

AI 엔지니어 마법사(한승우) 관점의 독립 서비스로, 상세 내용은 2.3절 참조.

### 2.2 서비스 간 통신 전략

| 통신 유형 | 적용 경로 | 이유 |
|---------|---------|------|
| **동기 REST (실선)** | 클라이언트 → API Gateway → 각 서비스 | 사용자가 응답을 기다리는 요청. 즉각 응답 필요. |
| **동기 REST (실선)** | 추천·이력 서비스 → AI Pipeline 서비스 | 추천 결과가 즉시 반환되어야 하므로 동기. 단, Circuit Breaker로 장애 격리. |
| **동기 REST (실선)** | 추천·이력 서비스 → 회원 서비스 (취향 조회) | 추천 생성 전 취향 벡터 조회. 동기 필요. |
| **비동기 메시지 (점선)** | 결제 서비스 → 메시지 큐 → 회원 서비스 | 결제 완료 후 구독 상태 갱신은 즉각성이 불필요. 결제 서비스와 회원 서비스 결합도 최소화. |
| **Cache-Aside (점선)** | 추천·이력 서비스 ↔ Redis | 추천 결과 캐싱. 캐시 미스 시 AI Pipeline 호출 후 캐싱. |

### 2.3 AI 서비스 아키텍처 (마법사 관점)

#### AI Pipeline 서비스 독립 식별 근거

추천·이력 서비스 내에 LLM 호출 로직을 내장하면 다음 문제가 발생한다.

- LLM 장애가 추천·이력 서비스 전체를 마비시킨다.
- LLM API 업그레이드(모델 교체)가 추천·이력 서비스 배포를 요구한다.
- 프롬프트 튜닝이 추천 로직 변경과 함께 릴리즈된다.

AI Pipeline을 독립 서비스로 분리함으로써 LLM 의존성을 캡슐화하고, 폴백 전략의 적용 범위를 명확히 한다.

#### AI Pipeline 서비스 책임

| 책임 | 상세 |
|------|------|
| **LLM API 호출** | Anthropic Claude / OpenAI GPT. `init_chat_model`로 모델을 추상화하여 제공자 전환 시 코드 변경 최소화. |
| **프롬프트 관리** | 컨텍스트(취향 벡터, 위치, 날씨, 요일, 최근 이력)를 프롬프트로 조립. 프롬프트 버전 관리 내부 수행. |
| **추천 이유 생성** | "비 오는 날 + 어제 양식 → 따뜻한 한식 추천" 형태의 자연어 한 줄 이유 생성 (A8). |
| **확신 스코어 계산** | 상위 3개 추천의 확률(%) 계산 및 반환. |
| **폴백 추천** | LLM Circuit Breaker가 Open 상태일 때 규칙 기반 추천(지역 인기 메뉴 + 거리 기반 정렬) 반환. |

#### 기술 스택

| 항목 | 선택 | 이유 |
|------|------|------|
| 언어/프레임워크 | Python / FastAPI | LLM SDK(langchain-anthropic, openai) 생태계 최적화. 비동기 처리 성능. |
| LLM 추상화 | `langchain_core.language_models.init_chat_model` | Claude/GPT 모델 전환 시 환경변수 변경만으로 교체 가능. |
| LLM API | Claude (기본), GPT (대체) | init_chat_model로 추상화하여 제공자 종속성 최소화. |

#### 적용 패턴

| 패턴 | 적용 위치 | 동작 |
|------|---------|------|
| **Circuit Breaker** | LLM API 호출 레이어 | 연속 5회 실패 시 Open. Open 상태에서는 즉시 폴백(규칙 기반 추천) 반환. Half-Open으로 복구 감지. |
| **Cache-Aside** | 추천 결과 캐시 | 추천 요청 수신 시 Redis에서 캐시 확인. 미스 시 LLM 호출 후 결과를 Redis에 TTL(당일 13:00)로 저장. |
| **Rate Limiting** | LLM API 호출 레이어 | 글로벌: 분당 500회 (LLM 제공자 RPM의 80%). 사용자별: 분당 10회. |
| **Retry** | LLM API 호출 레이어 | 지수 백오프(500ms → 1초 → 2초) + 지터. 최대 3회. 503/408/일시적 429에만 적용. |

#### 폴백 전략

```
LLM Circuit Breaker 상태 확인
├── Closed (정상): LLM API 호출 → 결과 반환 + Redis 캐싱
├── Open (장애): 폴백 즉시 실행
│   ├── 캐시 데이터 존재 → 캐시된 추천 반환 (만료 데이터 허용, 안내 메시지 포함)
│   └── 캐시 없음 → 규칙 기반 추천 (위치 반경 500m 인기 메뉴 + 알레르기 필터 적용)
└── Half-Open: 제한적 LLM 호출로 복구 확인
```

#### 콜드스타트 안전망 (UFR-REC-030)

피드백 5건 미만 신규 사용자의 경우 LLM 입력으로 사용할 취향 벡터가 부족하다. AI Pipeline은 다음 순서로 처리한다.

1. 온보딩 퀴즈 결과(음식 카드 스와이프)를 취향 벡터 초기값으로 사용
2. 직군 클러스터 Bayesian Prior 적용(지역 인기 메뉴 가중치)
3. "아직 취향을 학습 중이에요" 안내 태그를 응답에 포함

## 3. 주요 사용자 플로우

### 플로우 1: 오늘의 추천 조회 (UFR-REC-010, A8)

```
[목표] 앱 진입 3초 이내 추천 3개 카드 + 자연어 이유 표시

클라이언트 → API Gateway (JWT 검증, Rate Limiting)
→ 추천·이력 서비스 (추천 조회 오케스트레이션)
  ├── 회원 서비스 조회: 취향 벡터, 알레르기 필터 (동기)
  ├── 날씨 API 조회 (Circuit Breaker + Retry)
  ├── Cache-Aside 확인
  │   ├── 캐시 Hit → Redis에서 추천 결과 즉시 반환 (< 200ms)
  │   └── 캐시 Miss → AI Pipeline 서비스 호출 (동기, Circuit Breaker)
  │       → LLM API: 추천 3개 + 자연어 이유 + 확신 스코어 생성 (< 3초)
  │       → Circuit Breaker Open 시: 규칙 기반 폴백 즉시 반환
  │       → 결과를 Redis에 캐싱 (TTL: 당일 13:00)
→ 클라이언트: 추천 카드 3개 표시

성공 기준: p95 < 3초 (캐시 히트 시 < 200ms)
```

### 플로우 2: 원탭 식사 기록 + 피드백 (UFR-REC-070, UFR-REC-090, A5)

```
[목표] "먹었어요" 1탭 → 기록 완료 → 피드백 10초 내 제출

클라이언트 → API Gateway
→ 추천·이력 서비스 (식사 기록 저장)
  → 동일 식사 중복 기록 방지 (멱등성 체크)
  → 식사 기록 DB 저장 (회원ID, 식당ID, 식사시간, 수락된 추천ID)
  → Redis 해당 사용자 추천 캐시 무효화 (취향 변화 반영 위해)
→ 클라이언트: "오늘 점심 기록 완료!" + 피드백 화면

피드백 제출:
클라이언트 → 추천·이력 서비스
→ 피드백 저장 (좋아요/별로, 선택 키워드)
→ "내일 추천에 반영할게요" 응답

성공 기준: p95 < 200ms
```

### 플로우 3: 일일 취향 학습 (UFR-REC-100, A1)

```
[목표] 매일 03:00 배치 실행 → 취향 벡터 갱신 → 다음 날 추천 품질 향상

스케줄러 (매일 03:00)
→ 추천·이력 서비스 (배치 취향 학습)
  → 전일 피드백 전체 수집
  → 사용자별 취향 벡터 갱신 (최근 피드백 가중치 > 과거)
  → 콜드스타트 확인: 피드백 5건 미만 → 안전망 유지
  → 학습 반영 메시지 생성 ("어제 별로라고 한 매운 음식을 빼고 추천했어요")
  → 회원 서비스 취향 벡터 갱신 API 호출
  → Redis 해당 사용자 추천 캐시 전체 무효화 (갱신된 취향 반영)
  → 실패 시: 이전 취향 벡터 유지 (서비스 영향 없음)

성공 기준: 갱신 실패율 < 1% / 갱신 완료 시 다음 추천에 즉시 반영
```

### 플로우 4: 구독 결제 (UFR-PAY-020, A1)

```
[목표] 결제 완료 → 프리미엄 즉시 활성화 → 이력 보관 무제한 전환

클라이언트 → API Gateway
→ 결제 서비스 (결제 처리)
  → PG 결제 요청 (Circuit Breaker, Retry 미적용)
  → 결제 성공 → 결제 이력 DB 저장
  → 구독 상태 갱신 이벤트 발행 → 메시지 큐 (Redis Streams)
  → 클라이언트: "프리미엄 활성화 완료" 즉시 응답

비동기 처리:
메시지 큐 → 회원 서비스 (구독 상태 갱신 소비)
  → 구독 상태: 무료 → 프리미엄 갱신
  → 이력 보관 기간: 30일 → 무제한 갱신

성공 기준: 결제 완료 응답 p95 < 3초 / 이중결제 0건
```

## 4. 데이터 흐름 및 캐싱 전략

### 4.1 Cache-Aside 적용 범위

| 캐시 대상 | 캐시 키 구조 | TTL | 무효화 트리거 |
|---------|-----------|-----|------------|
| 추천 결과 | `rec:{user_id}:{location_grid}:{weather_code}:{weekday}` | 당일 13:00 | 피드백 저장, 식사 기록, 취향 벡터 갱신 |
| 구독 플랜 정보 | `plan:list` | 1시간 | 플랜 변경 시 관리자 수동 무효화 |
| JWT 블랙리스트 | `jwt:blacklist:{jti}` | 토큰 만료 시간 | 자동 만료 |
| 세션 정보 | `session:{user_id}` | 1시간 | 로그아웃 시 |

### 4.2 데이터 격리 원칙

각 서비스는 자신의 PostgreSQL DB만 직접 접근한다. 다른 서비스의 데이터가 필요할 경우 반드시 해당 서비스의 API를 호출한다.

```
회원 DB       ← 회원 서비스만 직접 접근
추천·이력 DB  ← 추천·이력 서비스만 직접 접근
결제 DB       ← 결제 서비스만 직접 접근
```

### 4.3 주요 데이터 흐름

```
[추천 데이터 흐름]
클라이언트 요청
→ 추천·이력 서비스
→ (회원 서비스 API) 취향 벡터 + 알레르기 필터 조회
→ (날씨 API) 현재 날씨 조회
→ Redis 캐시 확인
  → Hit: 캐시 결과 반환
  → Miss: AI Pipeline API 호출
         → LLM API (Claude/GPT)
         → 추천 3개 + 이유 + 확신 스코어 반환
         → Redis 캐싱
→ 클라이언트 응답

[식사 기록 데이터 흐름]
클라이언트 "먹었어요" 탭
→ 추천·이력 서비스
→ 식사 기록 DB 저장
→ Redis 추천 캐시 무효화 (해당 사용자)
→ 피드백 화면 전환

[구독 상태 데이터 흐름]
결제 서비스 → 결제 DB 저장 → 메시지 큐 발행
→ 회원 서비스 소비 → 회원 DB 구독 상태 갱신
```

## 5. 확장성 및 성능 고려사항

### 5.1 피크타임 대응 (12~13시, 동시 1,000명)

| 전략 | 적용 방식 | 효과 |
|------|---------|------|
| **Cache-Aside** | 추천 결과 Redis 캐싱. 동일 컨텍스트 재요청 시 LLM 호출 없이 응답. | LLM 호출 70~90% 감소. 캐시 히트 시 응답 < 200ms. |
| **Rate Limiting** | API Gateway에서 사용자별 분당 10회, 글로벌 LLM 분당 500회 제한. | LLM 비용 예측 가능, 할당량 초과 방지. |
| **Circuit Breaker** | LLM 연속 5회 실패 시 Open → 폴백(규칙 기반) 즉시 응답. | 피크타임 cascade failure 방지. |
| **Health Endpoint** | `/health` 엔드포인트에서 서비스 상태 + Circuit Breaker 상태 노출. | 오토스케일링 트리거 연동. CPU 70% 이상 시 자동 확장. |

### 5.2 응답 시간 목표

| API | 목표 (p95) | 달성 전략 |
|-----|-----------|---------|
| 추천 조회 (캐시 히트) | < 200ms | Redis 직접 응답 |
| 추천 조회 (캐시 미스, LLM 포함) | < 3초 | LLM 비동기 내부 처리, Retry 최대 3회 |
| 식사 기록 | < 200ms | DB 단순 Insert, 캐시 무효화 |
| 이력 조회 | < 500ms | PostgreSQL 인덱스(user_id, meal_date) |
| 구독 플랜 조회 | < 200ms | Redis 캐싱 (TTL 1시간) |

### 5.3 확장성 설계 고려사항

현재 단계(MVP)에서 물리적 확장 방식은 결정하지 않는다. 논리 수준에서 다음 원칙을 준수하여 향후 수평 확장이 가능하도록 설계한다.

- **상태 비저장(Stateless) API**: 각 서비스는 요청 상태를 로컬에 보관하지 않는다. 세션 상태는 Redis에 저장.
- **DB 커넥션 풀**: 서비스별 최대 100개 유지 원칙. 피크타임 커넥션 부족 방지.
- **서비스 간 느슨한 결합**: 결제→회원 비동기 메시지로 직접 의존 제거.

## 6. 보안 고려사항

### 6.1 인증/인가

| 항목 | 설계 |
|------|------|
| **소셜 로그인** | 카카오 OAuth 2.0. 카카오 토큰 검증 후 내부 JWT 발급. |
| **JWT 접근 토큰** | 만료 시간 1시간. API Gateway에서 검증 후 서비스에는 사용자 컨텍스트만 전달. |
| **JWT 블랙리스트** | 로그아웃 시 Redis에 토큰 JTI 등록. 접근 토큰 만료 시까지 유지. |
| **서비스 간 통신** | API Gateway 내부망에서만 서비스 접근 허용. 서비스 직접 외부 노출 없음. |

### 6.2 데이터 암호화

| 항목 | 설계 |
|------|------|
| **전송 암호화** | TLS 1.3. API Gateway에서 TLS 종료. |
| **개인정보 저장** | 이메일, 위치 정보: AES-256 암호화 저장. |
| **민감정보 저장** | 알레르기/식이제한: 별도 암호화 키로 AES-256 저장. |
| **위치 정보 보관** | 위치정보법 준수: 6개월 보유 후 자동 삭제. |

### 6.3 법규 준수

| 법규 | 준수 방식 |
|------|---------|
| **위치정보법** | 위치 수집 전 명시적 동의(UFR-MBR-030), 6개월 보유 후 자동 삭제, 위치 정보 수집 목적 고지. |
| **개인정보보호법** | 최소 수집 원칙. 알레르기(민감정보) 별도 동의. 개인정보 접근 로그 6개월 보관. |
| **전자상거래법** | 구독 청약철회권 7일 보장(UFR-PAY-030), 자동 갱신 고지, 해지 방법 명시. |

### 6.4 Health Endpoint 보안

`/health` 엔드포인트는 내부 VPC에서만 접근 허용. 외부 공개 시 서비스 내부 상태(Circuit Breaker 상태, DB 연결 상태) 정보 노출 위험이 있으므로 퍼블릭 엔드포인트에서 제외한다.
